1. ERRO: policy_engine/policy/rego/genoma.rego (Linhas 9-15)
   ───────────────────────────────────────────────────────────────────────────
   PROBLEMA:
   - Falta tratamento para quando "ruleset" está ausente completamente
   - Sem o primeiro "deny", um manifesto sem "ruleset" é permitido (PASS)
   - Todos os checks subsequentes ficariam "undefined" (sem rejeição)

   SOLUÇÃO:
   Adicionar verificação obrigatória no início dos checks:
   
   ```rego
   deny contains "RULESET: ruleset block is required" if not is_object(object.get(input, "ruleset", null))
   ```
   
   STATUS: ✓ CORRIGIDO NA PR (linha 12-13)


2. ERRO: mcp/src/server.ts (Linhas 53-129)
   ───────────────────────────────────────────────────────────────────────────
   PROBLEMA:
   - Função runFixedScript usa execFile que não cria grupo de processos
   - Timeout mata apenas o processo direto, deixando descendentes rodando
   - Scripts como "scripts/run_canary.sh" iniciam pipelines em background
   - Remanescentes consomem recursos e testam contra resultados incorretos

   SOLUÇÃO:
   - Mudar de execFile para spawn com detached: true
   - Usar processo.kill(-pid) para POSIX (sinaliza grupo inteiro)
   - Implementar dois estágios: SIGTERM (gracioso) + SIGKILL (força)
   - Adicionar constantes de timeout:
     * GROUP_TERMINATION_GRACE_MS = 5_000
     * USE_PROCESS_GROUP = process.platform !== "win32"

   STATUS: ✓ CORRIGIDO NA PR (linhas 75-157)


3. ERRO: mcp/src/server.ts (Linhas 105-145)
   ───────────────────────────────────────────────────────────────────────────
   PROBLEMA:
   - Leitura de stdout com maxBuffer fixo não previne truncamento
   - Mensagens de erro grandes são perdidas silenciosamente
   - Apenas últimos bytes de stderr são conservados

   SOLUÇÃO:
   - Ler stdout em chunks, verificar total de bytes
   - Se exceder limite (SCRIPT_OUTPUT_MAX_BYTES = 5MB):
     * Setar flag "overflowed"
     * Matar processo com SIGKILL
     * Lançar erro informativo
   - Manter últimos 4KB de stderr (STDERR_TAIL_MAX_BYTES)

   STATUS: ✓ CORRIGIDO NA PR (linhas 72-92, 95-108)


4. ERRO: mcp/src/server.ts (Linhas 258-295)
   ───────────────────────────────────────────────────────────────────────────
   PROBLEMA:
   - Race condition: múltiplos callers com mesmo requestId podem executar em paralelo
   - Dois processadores podem ambos passar pelo check de "prior result"
   - Ambos executam operation(), resultados divergem

   SOLUÇÃO:
   - Implementar O_EXCL no arquivo de "claim":
     ```typescript
     const handle = await open(claimPath, "wx", 0o600)
     ```
   - Apenas um caller consegue criar o arquivo (atomic)
   - Losers detectam EEXIST e falham com "already in progress"
   - Liberar claim no finally para permitir retry

   STATUS: ✓ CORRIGIDO NA PR (linhas 197-243, 263-310)


5. ERRO: scripts/sealed_ruleset.py (Linhas 226-244)
   ───────────────────────────────────────────────────────────────────────────
   PROBLEMA:
   - Função _already_materialized não verifica symlinks
   - Arquivo reusável pode ser symlink → permite substituição de identidade
   - Modo verificado com .stat() (segue symlink), não .lstat() (próprio arquivo)

   SOLUÇÃO:
   - Usar os.lstat() em vez de .stat() para modo (não segue symlink)
   - Verificar: existing.is_symlink() ou not existing.is_file()
   - Comparar modo esperado EXATAMENTE com 0o444:
     ```python
     if mode != 0o444:  # não apenas "não tem bits de write"
     ```

   STATUS: ✓ CORRIGIDO NA PR (linhas 243-249)


6. ERRO: scripts/validate_repo.py (Linhas 261-270)
   ───────────────────────────────────────────────────────────────────────────
   PROBLEMA:
   - Função _identity_declaration_strings silencia SyntaxError
   - Arquivo Python malformado é ignorado = nunca validado
   - Identidade supersedida em código quebrado passa despercebida

   SOLUÇÃO:
   - Reportar SyntaxError e marcar como erro:
     ```python
     except SyntaxError as exc:
         errors.append(f"unparseable Python: {relative}: {exc.msg} (line {exc.lineno})")
         continue
     ```
   - Continuar validação para outros arquivos

   STATUS: ✓ CORRIGIDO NA PR (linhas 348-352)


7. ERRO: evidence_adapters/__init__.py (Linhas 53-65)
   ───────────────────────────────────────────────────────────────────────────
   PROBLEMA:
   - response.read(MAX_RESPONSE_BYTES + 1) pode timeouts indefinidos
   - Resposta lenta/streaming pode bloquear aguardando MAX_RESPONSE_BYTES+1
   - Sem timeout específico, connection.read() espera por sempre

   SOLUÇÃO:
   - Ler em chunks de 64KB
   - Monitorar total acumulado
   - Se total > MAX_RESPONSE_BYTES, abortar (EOF e erro)
   - Usar loop com verificação de bytes:
     ```python
     while total <= MAX_RESPONSE_BYTES:
         chunk = response.read(min(64*1024, MAX_RESPONSE_BYTES+1-total))
         if not chunk: break
         chunks.append(chunk)
         total += len(chunk)
     ```

   STATUS: ✓ CORRIGIDO NA PR (linhas 56-65)


8. ERRO: evidence_adapters/__init__.py (Linhas 226-235)
   ───────────────────────────────────────────────────────────────────────────
   PROBLEMA:
   - Log de erro não inclui traceback completo (exc_info=True ausente)
   - Root cause (TLS rejection, timeout, oversized) indistinguível nos logs
   - Operador não consegue diagnosticar por que adaptador falhou

   SOLUÇÃO:
   - Adicionar exc_info=True ao LOGGER.warning:
     ```python
     LOGGER.warning(
         "evidence retrieval failed adapter=%s error_class=%s",
         self.key, type(exc).__name__,
         exc_info=True,  # ← adicionado
     )
     ```

   STATUS: ✓ CORRIGIDO NA PR (linhas 243-248)
